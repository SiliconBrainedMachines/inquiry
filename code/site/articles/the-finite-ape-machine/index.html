The Finite APE Machine

The origin of Analyze → Plan → Execute

May 13, 2026 origin methodology philosophy

Late 2022. ChatGPT had just been released. Like millions of others, I started using AI for software development. The promise was immediate: describe what you want, get code back.

The reality was different.

The AI assumed things I hadn't said. It misinterpreted ambiguous requests. It produced plausible but wrong solutions with absolute confidence. And most of the time, the fault was mine — I expressed myself with the ambiguity natural to human language and expected the machine to read my intent. It didn't. It read my words.

The bottleneck was never the AI. The bottleneck was me.

The Runbook

My first attempt at solving this was instinctive, not theoretical. I created a custom agent — a system prompt — whose only job was to generate a file called runbook.md. Before writing any code, the agent would analyze what I wanted and produce a step-by-step plan: what to change, in what order, what tests to write, what to verify.

It was crude. No formal methodology. No philosophical foundation. Just a developer frustrated with AI that jumped straight to code and got it wrong, building a guardrail to force the machine to think before acting.

But it worked. The code quality improved immediately. Not because the AI got smarter — because I got clearer. The runbook forced me to articulate what I actually wanted before the AI touched anything. By the time it started coding, the problem was already solved. What remained was mechanical transcription.

I didn't realize it at the time, but that runbook was the ancestor of everything that came after.

The Pattern

Months of iteration revealed a structure hiding inside my workflow. Every successful cycle followed the same three phases:

  1. Analyze — understand the problem before proposing solutions
  2. Plan — decompose the solution into ordered, verifiable steps
  3. Execute — implement against the plan, not against vague intent

Every time I skipped analysis and jumped to planning, the plan was wrong. Every time I skipped planning and jumped to code, the code was wrong. The sequence was not a preference — it was a constraint. Violating it produced predictable failures.

This wasn't a new discovery. I was rediscovering what software engineering has known for decades under different names: spec-driven development, test-driven development, design-before-code. The difference was the context — I was applying it to human-AI collaboration, where the communication gap makes these disciplines not just useful but essential.

Spec-Driven, Test-Driven

The foundation crystallized around two established practices:

Spec-driven development — write the specification before writing the code. In the AI context, this means the analysis phase produces a diagnosis that captures requirements, assumptions, edge cases, and constraints. By the time the AI sees the problem, ambiguity has been eliminated. The spec is the contract.

Test-driven development — write the tests before writing the implementation. Tests are unambiguous. Tests don't drift. When you hand an AI a failing test and say "make this pass," the result is either correct or it isn't. No room for plausible-but-wrong. No room for creative interpretation.

The most reliable way to get correct output from an AI is to give it a failing test. Tests are the only language where human intent and machine execution have zero ambiguity.

Together, spec-driven and test-driven development gave me a methodology where the AI's tendency to hallucinate became irrelevant. By the time it writes code, the problem is defined, the plan is explicit, and the tests are waiting. The AI is no longer guessing — it's transcribing.

The Sub-Agents

The next leap was realizing that the methodology itself could be encoded as agents. Instead of one monolithic prompt that says "be careful and follow the process," what if each phase had its own specialized agent — one that embodies the method, not just follows instructions?

I looked for the best practitioners of each discipline. Not in tech. In human intellectual history.

  • SOCRATES for analysis — because the Socratic method (mayéutica) is 2,400 years of refined practice in drawing truth through questioning, not assertion
  • DESCARTES for planning — because the Cartesian method (divide, order, verify, enumerate) is the most rigorous decomposition framework ever written
  • BASHŌ for execution — because the Japanese concept of yō no bi (用の美, beauty in function) captures what great code feels like: minimal, purposeful, where constraint reveals elegance

Each name identifies a thinking tool — a method of reasoning drawn from a specific philosopher, culture, and era. The diversity is intentional. The tools span 2,400 years, three cultures, and three disciplines. The thesis: the best methodology for building software already exists, scattered across human intellectual history. We just had to assemble it.

Later, two more agents joined: DEWEY for issue triage (Deweyan problematization — turning an indeterminate situation into a well-formed problem), and DARWIN for evolution (natural selection applied to the methodology itself, so the system improves through its own operation).

The Machine

Agents with methods weren't enough. They needed structure — a system that enforces the sequence, prevents shortcuts, and makes every transition explicit.

That system is the Finite APE Machine: a finite-state machine with six states, deterministic transitions, and a contract that the AI cannot bypass.

IDLE → ANALYZE → PLAN → EXECUTE → END → IDLE
                                      ↘ EVOLUTION

Every transition requires explicit authorization. Ambiguous approval is not authorization — "ok" and "sounds good" do not move the state machine. The agent proposes; the human disposes. This is not a UX choice. It is a trust boundary.

The CLI (iq) is the kernel. Agents are userspace. Just as a Linux process does not write to /proc/, agents do not mutate the FSM state directly. All state changes go through the CLI, which validates preconditions before every transition. If the agent hallucinates a state change, the CLI rejects it.

The banner phrase

Infinite monkeys produce noise. Finite APEs produce software.

The infinite monkey theorem says that random input eventually produces any text — given infinite time. Inquiry rejects randomness. A finite number of disciplined agents, following a structured method, produce working software in finite time. The constraint is the point. The method is the machine.

From Runbook to Inquiry

The distance from that first runbook.md to the Finite APE Machine is measured in months, not years. But the intellectual distance is vast. What started as a frustrated developer building a guardrail became a methodology grounded in pragmatist philosophy, epistemology, and the history of scientific inquiry.

Charles Sanders Peirce proved in 1878 that all structured investigation follows three modes of inference: abduction (hypothesis), deduction (experimental design), and induction (empirical test). The APE cycle maps exactly:

Peirce's inquiry APE phase Agent
Abduction — inference to the best explanation ANALYZE SOCRATES
Deduction — derive consequences from hypotheses PLAN DESCARTES
Induction — test consequences against reality EXECUTE BASHŌ

The APE cycle wasn't just a workflow — it was an implementation of the oldest formal theory of structured investigation. That's when the project got its name: Inquiry.

John Dewey defined inquiry as "the controlled transformation of an indeterminate situation into one that is so determinate as to convert the elements of the original situation into a unified whole." A GitHub issue is an indeterminate situation. A merged pull request is a determinate unified whole. The APE cycle is the controlled transformation between them.

This is not a metaphor. It is an isomorphism.

The Bet

Inquiry makes a bet: methodology over model.

If the framework carries the weight — if analysis eliminates ambiguity, planning makes the solution explicit, and execution follows the spec — then the specific AI model matters less. A smaller or free model following a rigorous method should stay useful where a frontier model freestyling falls apart.

The unexpected result: I recognize the code the AI produces as my own. Not because I wrote it, but because I designed it. Every decision was made during analysis and planning. The AI implemented my design, following my conventions, under my constraints.

The methodology doesn't replace the engineer. It amplifies them.

And it started with a runbook.
