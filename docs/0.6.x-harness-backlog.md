# Inquiry 0.6.x Harness Backlog

**Tipo de documento:** backlog canónico de ejecución  
**Estado:** activo  
**Alcance:** `0.6.5 -> 0.6.99`

Este documento es la guía canónica de trabajo para la serie `0.6.x` de Inquiry.

Su función no es reemplazar [roadmap.md](roadmap.md). El roadmap sigue siendo estratégico e histórico. Este archivo, en cambio, existe para responder una pregunta más operativa:

> ¿Qué resultados debe dejar la consolidación del harness antes de `0.7.0`, en qué orden conviene abordarlos y cómo sabremos que cada bloque mejoró realmente el sistema?

## Cómo leer este backlog

Este backlog es **independiente del issue tracker**.

Los issues pueden servir como trazabilidad, coordinación o empaquetado de implementación, pero no definen el plan ni su criterio de éxito. Un bloque no está resuelto porque un ticket se haya cerrado; está resuelto cuando el runtime, la documentación y las validaciones exhiben de forma verificable las propiedades descritas aquí.

La pregunta principal no es “qué tickets faltan”, sino esta:

> ¿Qué capacidades debe ganar Inquiry para operar como un harness más explícito, más legible, más verificable y menos derrochador de contexto?

## Objetivo real de 0.6.x

Antes de `0.7.0`, Inquiry debe dejar atrás el estado de harness todavía parcialmente implícito y consolidarse como un harness deliberado para trabajo agentic de software.

Eso significa avanzar, en este orden, hacia cinco propiedades:

1. la tarea activa se expresa como contrato explícito y no como inferencia frágil
2. ANALYZE adquiere evidencia antes de interrogar al usuario
3. la política de contexto y la autoridad de handoffs dejan de ser implícitas
4. los sensores y gates mínimos por fase pasan a ser parte visible de la arquitectura
5. el propio harness deja trazas y métricas suficientes para auditar coste, fallos y retrabajo

## Misión de 0.6.x

Antes de `0.7.0`, Inquiry debe cerrar defectos base del harness y no distraerse con optimizaciones prematuras.

La misión de esta serie es:

1. volver explícito el contrato de tarea
2. hacer ANALYZE verdaderamente evidence-first
3. reducir duplicación de contexto entre orquestador, subagentes, artefactos y relecturas
4. formalizar sensores y gates mínimos
5. volver observable el overhead del propio harness

## Reglas operativas de la serie

- **Evidence before inference.** El análisis debe apoyarse primero en repo, artefactos, docs, tests y evidencia ejecutable.
- **Research before interrogation.** Antes de preguntar al usuario, Inquiry debe agotar repo y, cuando aplique, investigación externa acotada.
- **Context is a budget.** Duplicar contexto y relecturas es desperdicio del harness.
- **Authoritative handoffs.** `diagnosis.md`, `plan.md` y artefactos equivalentes deben funcionar como autoridad operativa entre fases.
- **Overhead is architecture.** Tiempo, herramientas, tokens, caché y reintentos son propiedades del sistema, no solo molestias de UX.
- **Results over tickets.** El programa se evalúa por mejoras reales del harness, no por la cantidad de issues cerradas.

## Definición global de éxito antes de 0.7.0

La serie `0.6.x` puede considerarse sustancialmente cumplida cuando estas condiciones se observan simultáneamente:

1. Inquiry tiene un task environment contract legible y usado por el runtime.
2. ANALYZE sigue un orden evidence-first explícito antes de preguntar al usuario.
3. Inquiry tiene una context policy por fase escrita y coherente con Memory as Code.
4. Inquiry tiene una taxonomía de sensores aplicada al menos en los puntos de cierre y handoff más críticos.
5. Inquiry registra suficiente evidencia para observar comportamiento del harness y no sólo resultados finales.

## Programa canónico de trabajo

### 1. Task Contract Foundation

**Objetivo**  
Hacer que la tarea activa deje de ser inferida y pase a ser un contrato explícito visible para el agente.

**Entregables mínimos**

1. `docs/spec/task-environment-contract.md`
2. extensión de `inquiry-context` con campos mínimos de contrato
3. definición operativa de `done_criteria` por fase
4. tratamiento explícito de `project_root`, `task_id`, superficies editables y read-only
5. criterio claro para dependencias externas o layouts complejos sin romper el bounded execution model

**Resultados deseados**

- el agente recibe un entorno de tarea explícito y acotado
- el prompt efectivo expone inputs, outputs, superficies editables y validaciones mínimas
- la tarea activa deja de depender de cwd, heurísticas frágiles o lectura implícita del repo
- la regla de una tarea por ciclo queda reforzada como invariante del contrato

**Criterio de cierre**

Este bloque está suficientemente resuelto cuando, desde el prompt efectivo y sin interpretación adicional frágil, el agente puede saber:

1. qué trabajo tiene asignado
2. qué puede tocar
3. qué debe producir
4. cómo demostrar que terminó

**Beneficio operativo**

Reduce ambigüedad estructural, baja el riesgo de deriva de tarea y vuelve el runtime menos dependiente de convenciones implícitas.

### 2. Evidence-First ANALYZE

**Objetivo**  
Hacer que ANALYZE investigue antes de preguntar y que SOCRATES deje de interrogar por inercia metodológica.

**Entregables mínimos**

1. política explícita de adquisición de evidencia para ANALYZE
2. orden claro entre repo, artefactos de ciclo, docs, tests, runtime evidence, web research y preguntas al usuario
3. reglas para distinguir síntesis justificada de interrogación innecesaria
4. fortalecimiento del diagnóstico como artefacto que separa hechos observados, hipótesis y dudas pendientes
5. capacidad de source gathering suficientemente amplia para no depender del usuario como primera fuente por defecto

**Resultados deseados**

- ANALYZE revisa primero repo, artefactos de cleanroom, docs, tests y evidencia ejecutable
- si eso no alcanza, realiza investigación externa acotada antes de interrogar al usuario
- SOCRATES pregunta menos, con más valor y con mejor grounding
- el diagnóstico deja explícito qué está observado, qué está inferido y qué sigue abierto

**Criterio de cierre**

Este bloque está suficientemente resuelto cuando:

1. una parte significativa de los ciclos puede completar ANALYZE sin interrogación innecesaria
2. las preguntas remanentes reducen incertidumbre real en vez de repetir trabajo que el repo ya podía resolver
3. `diagnosis.md` distingue con claridad evidencia, hipótesis, constraints y preguntas abiertas

**Beneficio operativo**

Mejora la calidad del diagnóstico, reduce preguntas de bajo valor y hace que el análisis sea más reproducible y menos dependiente de improvisación conversacional.

### 3. Context Policy and Authoritative Handoffs

**Objetivo**  
Reducir relecturas y reconstrucción redundante de contexto haciendo explícita la policy de contexto por fase y la autoridad de los handoffs.

**Entregables mínimos**

1. `docs/spec/context-policy.md`
2. definición por fase de contexto upfront, retrieval context y deferred context
3. reglas explícitas de autoridad para handoffs entre ANALYZE, PLAN y EXECUTE
4. criterios para cuándo releer, cuándo recuperar on-demand y cuándo confiar en el artefacto autoritativo
5. endurecimiento del comportamiento de skills y runtime frente a rereads redundantes

**Resultados deseados**

- `diagnosis.md` y `plan.md` tienen semántica de autoridad explícita
- el runtime y las skills distinguen entre contexto upfront y retrieval on-demand
- la reducción de rereads duplicados pasa a ser objetivo explícito del harness
- EXECUTE deja de reconstruir ANALYZE innecesariamente cuando ya existe un handoff suficiente

**Criterio de cierre**

Este bloque está suficientemente resuelto cuando puede explicarse, sin apelar a intuición del agente:

1. qué artefacto manda en cada handoff
2. qué contexto entra upfront por fase
3. qué contexto debe recuperarse sólo cuando aparece una ambigüedad concreta
4. cómo el sistema evita rereads amplios cuando ya existe autoridad operativa suficiente

**Beneficio operativo**

Reduce gasto de contexto, hace más legible el handoff entre fases y convierte Memory as Code en política operacional explícita, no sólo en una buena intuición.

### 4. Sensor Stack and END Discipline

**Objetivo**  
Pasar de checks dispersos a un modelo explícito de sensores, gates y validaciones mínimas por fase.

**Entregables mínimos**

1. `docs/spec/sensor-taxonomy.md`
2. definición de sensores mínimos por fase con foco inicial en EXECUTE y END
3. gate pre-PR explícito y legible para humano y agente
4. disciplina visible de release closure antes del handoff final
5. salida de transición suficientemente expresiva para mostrar trabajo declarado, no sólo metadata superficial
6. primer gate documental o linter que bloquee transiciones cuando el documento gobernante aún tiene pendientes relevantes

**Resultados deseados**

- existe una taxonomía de sensores con nombre, momento, autoridad, costo y efecto operativo
- EXECUTE y END tienen sensores mínimos documentados y aplicados
- END deja de depender del PR como ritual implícito de cierre
- las obligaciones de release y las operaciones autónomas declaradas dejan de quedar implícitas u ocultas
- los ítems pendientes detectables se bloquean en el punto correcto del ciclo, no sólo en gates tardíos

**Criterio de cierre**

Este bloque está suficientemente resuelto cuando:

1. existe una taxonomía de sensores escrita y estable
2. el camino de validación del ciclo es legible y ordenado por costo
3. END ya no depende sólo de “crear PR” como ritual de cierre
4. las transiciones críticas exponen con claridad qué validan, qué ejecutan y qué bloquean

**Beneficio operativo**

Mueve feedback útil hacia la izquierda, reduce sorpresas tardías y convierte el cierre del ciclo en arquitectura explícita en lugar de mezcla de convención humana y checks dispersos.

### 5. Harness Observability and Overhead Audit

**Objetivo**  
Hacer observable el coste real del harness y dejar evidencia suficiente para auditarlo y evolucionarlo.

**Entregables mínimos**

1. `docs/spec/harness-observability.md`
2. `docs/spec/eval-model.md`
3. trazas mínimas por ciclo y por fase sobre transiciones, sensores corridos, fallos detectados y retries
4. extensión prudente de métricas para capturar duración, coste operativo y puntos de bloqueo cuando la evidencia esté disponible
5. taxonomía inicial de fallos del harness

**Resultados deseados**

- el ciclo deja trazas suficientes para explicar coste por fase
- herramientas, tiempo, tokens, caché y retries dejan de ser opacos cuando la plataforma permite observarlos
- existe una diferencia clara entre métricas de resultado y trazas de ejecución del harness
- EVOLUTION puede apoyarse en evidencia de overhead y no sólo en impresiones narrativas

**Criterio de cierre**

Este bloque está suficientemente resuelto cuando el maintainer puede responder con evidencia preguntas como:

1. dónde se bloquea más el sistema
2. qué gates detectan más problemas útiles
3. qué retrabajo es recurrente
4. qué parte del coste pertenece al modelo, al host o al harness de Inquiry

**Beneficio operativo**

Convierte el overhead en evidencia arquitectónica y da base real para que DARWIN proponga mejoras sobre señales estructuradas, no sólo sobre lectura narrativa del ciclo.

## Resultados valiosos pero no críticos antes de 0.7.0

Estas líneas pueden seguir siendo valiosas dentro de `0.6.x`, pero no forman el camino crítico del backlog canónico de consolidación del harness:

- alineación más profunda con workflows de VS Code Agents y Copilot CLI
- superficies de distribución y conveniencia de producto
- autenticación o perfil de usuario como capability separada del núcleo del harness
- rediseño del website y otras superficies de identidad pública
- configuración dual-language para salidas user-facing

La regla es simple: no deben desplazar los bloques que hacen a Inquiry más contract-first, más sensorizado, más claro en contexto y más observable.

## Qué no hacer antes de 0.7.0

Mientras este backlog no esté sustancialmente resuelto, no conviene priorizar:

- modos configurables de profundidad
- presupuestos explícitos por fase
- reactivación multi-target completa como foco principal
- nuevos APEs para tapar defectos del harness
- memoria externa como sustituto prematuro de Memory as Code
- cerrar tickets como proxy de avance real del programa

## Secuencia recomendada para arrancar desarrollo

1. cerrar Task Contract Foundation
2. atacar Evidence-First ANALYZE
3. formalizar Context Policy and Authoritative Handoffs
4. ordenar Sensor Stack and END Discipline
5. cerrar Harness Observability and Overhead Audit

La secuencia no existe para honrar tickets antiguos, sino para proteger la arquitectura:

- primero se acota la tarea
- luego se mejora cómo se adquiere evidencia
- luego se ordena la política de contexto y la autoridad de handoffs
- después se consolidan los sensores y gates mínimos
- finalmente se mide el comportamiento del propio harness con mejor semántica

## Cómo saber si el plan avanza de verdad

Un bloque del plan avanza de verdad cuando se observan estas señales en conjunto:

- existe una spec breve y operativa
- el runtime o el prompt efectivo ya usan esa capacidad
- hay validación o evidencia ejecutable que demuestra el cambio de comportamiento
- la documentación canónica y el comportamiento real dejaron de contradecirse

Un bloque no debería darse por sustancialmente cumplido sólo porque exista prosa nueva, porque un issue haya cambiado de estado o porque haya un commit aislado sin efecto operativo observable.
