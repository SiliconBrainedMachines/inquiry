# Inquiry 0.6.x Harness Backlog

**Tipo de documento:** backlog canónico de ejecución  
**Estado:** activo  
**Alcance:** `0.6.5 -> 0.6.99`

Este documento es la guía canónica de trabajo para la serie `0.6.x` de Inquiry.

Su función no es reemplazar [roadmap.md](roadmap.md). El roadmap sigue siendo estratégico e histórico. Este archivo, en cambio, existe para responder una pregunta más operativa:

> ¿Qué issues forman el backlog real de consolidación del harness antes de `0.7.0`, en qué orden conviene abordarlas y qué resultado debe dejar cada bloque?

## Misión de 0.6.x

Antes de `0.7.0`, Inquiry debe cerrar defectos base del harness y no distraerse con optimizaciones prematuras.

La misión de esta serie es:

1. volver explícito el contrato de tarea
2. hacer ANALYZE verdaderamente evidence-first
3. reducir duplicación de contexto entre orquestador, subagentes, artefactos y relecturas
4. formalizar sensores y gates mínimos
5. volver observable el overhead del propio harness

## Reglas operativas de la serie

- **Evidence before inference.** El análisis debe apoyarse primero en repo, artefactos, docs, tests y evidencia ejecutable.
- **Research before interrogation.** Antes de preguntar al usuario, Inquiry debe agotar repo y, cuando aplique, investigación externa acotada.
- **Context is a budget.** Duplicar contexto y relecturas es desperdicio del harness.
- **Authoritative handoffs.** `diagnosis.md`, `plan.md` y artefactos equivalentes deben funcionar como autoridad operativa entre fases.
- **Overhead is architecture.** Tiempo, herramientas, tokens, caché y reintentos son propiedades del sistema, no solo molestias de UX.

## Orden canónico de trabajo

### 1. Task Contract Foundation

**Objetivo**  
Hacer que la tarea activa deje de ser inferida y pase a ser un contrato explícito visible para el agente.

**Issue ancla**

- [#219](https://github.com/ccisnedev/inquiry/issues/219) — define task environment contract and extend inquiry-context for bounded execution

**Issues de apoyo**

- [#178](https://github.com/ccisnedev/inquiry/issues/178) — Persist project root in inquiry context so iq is not cwd-dependent
- [#49](https://github.com/ccisnedev/inquiry/issues/49) — Enforce single-task-per-cycle rule in IDLE and ANALYZE
- [#60](https://github.com/ccisnedev/inquiry/issues/60) — Cross-repo dependency chains need explicit plan guidance
- [#149](https://github.com/ccisnedev/inquiry/issues/149) — workspace discovery for multi-root and nested repos

**Resultado esperado**

- existe spec de task environment
- `inquiry-context` expone inputs, outputs, superficies editables y validaciones
- la tarea activa puede verse en el prompt efectivo sin inferencia frágil

### 2. Evidence-First ANALYZE

**Objetivo**  
Hacer que ANALYZE investigue antes de preguntar y que SOCRATES deje de interrogar por inercia metodológica.

**Issues ancla**

- [#223](https://github.com/ccisnedev/inquiry/issues/223) — make ANALYZE evidence-first before questioning the user
- [#218](https://github.com/ccisnedev/inquiry/issues/218) — refine SOCRATES question relevance and self-service analysis

**Issue de apoyo**

- [#147](https://github.com/ccisnedev/inquiry/issues/147) — extend deep research into broader source gathering capability

**Resultado esperado**

- ANALYZE define un orden explícito de adquisición de evidencia
- SOCRATES pregunta menos y con mayor valor diagnóstico
- las preguntas al usuario quedan reservadas para hechos irresolubles desde el repo o para juicios humanos genuinos
- el diagnóstico distingue evidencia, hipótesis y preguntas abiertas

### 3. Context Policy and Authoritative Handoffs

**Objetivo**  
Reducir relecturas y reconstrucción redundante de contexto haciendo explícita la policy de contexto por fase y la autoridad de los handoffs.

**Issue ancla**

- [#220](https://github.com/ccisnedev/inquiry/issues/220) — formalize context policy and authoritative handoffs to cut duplicate rereads

**Issue de apoyo**

- [#167](https://github.com/ccisnedev/inquiry/issues/167) — single-phase BASHO dispatch to prevent context dilution

**Resultado esperado**

- existe `context-policy` como spec canónica
- `diagnosis.md` y `plan.md` tienen semántica de autoridad explícita
- el runtime y las skills distinguen entre contexto upfront y retrieval on-demand
- la reducción de rereads duplicados pasa a ser objetivo explícito del harness

### 4. Sensor Stack and END Discipline

**Objetivo**

**Issue ancla**

- [#221](https://github.com/ccisnedev/inquiry/issues/221) — define sensor taxonomy and minimum sensor stack for Inquiry phases

**Issues de apoyo**

- [#163](https://github.com/ccisnedev/inquiry/issues/163) — formal pre-PR inspection gate in EXECUTE phase
- [#127](https://github.com/ccisnedev/inquiry/issues/127) — EXECUTE must propose and get approval for semver bump before END
- [#207](https://github.com/ccisnedev/inquiry/issues/207) — END transitions skip declared autonomous operations
- [#29](https://github.com/ccisnedev/inquiry/issues/29) — document linter/gate to block transitions with pending items

**Resultado esperado**

- existe taxonomía de sensores
- EXECUTE y END tienen sensores mínimos documentados
- el gate pre-PR deja de ser ritual implícito y pasa a parte de la arquitectura

**Objetivo**  
Hacer observable el coste real del harness y dejar evidencia suficiente para auditarlo y evolucionarlo.

**Issues ancla**

- [#222](https://github.com/ccisnedev/inquiry/issues/222) — add harness observability and overhead metrics for cycle execution
- [#216](https://github.com/ccisnedev/inquiry/issues/216) — model a direct-use skill for inquiry cycle audit and LLM usage analysis

**Issues de apoyo**

- [#156](https://github.com/ccisnedev/inquiry/issues/156) — add GitHub platform usage metrics to the research dataset

- herramientas, tiempo, tokens, caché y retries dejan de ser opacos
- EVOLUTION puede apoyarse en evidencia de overhead y no solo en impresiones narrativas

## Qué no hacer antes de 0.7.0

Mientras este backlog no esté sustancialmente resuelto, no conviene priorizar:

- modos configurables de profundidad
- presupuestos explícitos por fase
- reactivación multi-target completa como foco principal
- nuevos APEs para tapar defectos del harness
- memoria externa como sustituto prematuro de Memory as Code

## Secuencia recomendada para arrancar desarrollo

1. cerrar Task Contract Foundation alrededor de [#219](https://github.com/ccisnedev/inquiry/issues/219)
2. atacar Evidence-First ANALYZE con [#223](https://github.com/ccisnedev/inquiry/issues/223) y [#218](https://github.com/ccisnedev/inquiry/issues/218)
3. formalizar Context Policy and Authoritative Handoffs con [#220](https://github.com/ccisnedev/inquiry/issues/220)
4. ordenar Sensor Stack and END Discipline con [#221](https://github.com/ccisnedev/inquiry/issues/221), [#163](https://github.com/ccisnedev/inquiry/issues/163), [#127](https://github.com/ccisnedev/inquiry/issues/127) y [#207](https://github.com/ccisnedev/inquiry/issues/207)
5. cerrar Harness Observability and Overhead Audit con [#222](https://github.com/ccisnedev/inquiry/issues/222) y [#216](https://github.com/ccisnedev/inquiry/issues/216)

Si esta secuencia se respeta, Inquiry llegará a `0.7.0` con una base de harness más nítida, más auditable y menos derrochadora de contexto.
